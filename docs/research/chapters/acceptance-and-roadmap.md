# Проверка прототипа и план пилота

Цель следующего выпуска — показать воспроизводимый осмотр конкретного агрегата с понятными источниками каждого вывода. Успешная демонстрация интерфейса, корректность программных правил и качество диагностики измеряются отдельно. Для команды это три разных результата и три разных протокола проверки.

## Подтверждённый результат разработки

На 13 ноября 2026 года стенд работает на сервере RTX 3090 Ti через HTTPS. Проверены 45 автоматических тестов на ноутбуке и Windows-сервере, сценарии в Chromium и мобильном WebKit, хранение двух тестовых осмотров и их повторное чтение. Полный путь кадра проверен через браузер с тестовым видеопотоком и реальным запросом на локальный GPU. Два изображения насоса получили предварительное наблюдение и рамку; белый кадр дал `unusable`. Это проверка прохождения запроса, а не измерение точности компьютерного зрения.

Для Qwen3-VL подтверждена загрузка модели в видеопамять. Физические камеры iPhone и Android и диалог входа на конкретных телефонах команда ещё должна проверить. Встроенные фотографии экрана камеры используют заранее заданный JSON. В презентации их следует называть демонстрационными сценариями.

CatBoost обучен на 2 205 циклах UCI с разделением по порядку циклов 60/20/20. На последних 441 циклах accuracy 53,1%, macro-F1 0,365; ни один из 123 случаев сильной внутренней утечки не определён верно. Артефакт исключён из рабочих заключений. [Воспроизводимый эксперимент](../../ml/benchmark-uci.md) и [полный отчёт](../../ml/uci-benchmark-report.json) фиксируют результат, включая неудачные случаи.

## Приёмка программной логики

| Проверка | Действие | Критерий результата |
| --- | --- | --- |
| Каждое правило | Подать все необходимые условия | Возвращены ожидаемый код, объяснение и зоны |
| Неполные данные | Убрать ключевой вход | Не возникает ложного подтверждения |
| Порог | Значения ниже, на границе и выше | Сравнение соответствует описанию правила |
| Несколько выводов | Совместить кожух, утечку и ТО | Критические сообщения не потеряны |
| Кавитация | Подать оба варианта условия | Подтверждённый вариант не дублирует предварительный |
| История | Повторить запрос с тем же ID | Одна запись; изменённые данные дают конфликт |
| Ошибочный ввод | Чужой serial, неверный JSON | Понятный отказ; нет повреждения записей |

Текущие тесты доказывают поведение кода на заданных примерах. Они не устанавливают диагностическую достоверность диагноза и не заменяют испытаний на оборудовании. Для будущего импортера добавляется отдельная проверка единиц измерения и временных окон; текущий `/api/diagnose` принимает уже нормализованные признаки. В разработке достаточно ссылаться на номера тестов и конкретный commit; в промышленном пилоте добавляются независимые инженерные подтверждения.

## Приёмка камеры и сервера

На каждом физическом устройстве записывают модель телефона, ОС, браузер или версию WebView, сеть и дату. Проверяют вход, отказ и выдачу разрешения камеры, заднюю камеру, портретную и альбомную ориентацию, возвращение из фона, фиксацию кадра и повторную съёмку. Снимок должен оставаться привязанным к рамке; при новом кадре старый вывод должен исчезать.

Отдельно проверяют плохой свет, блик, закрытый компонент, посторонний объект, отсутствие сети, недоступную модель и одновременную работу двух операторов. Для каждого случая требуется понятный статус. При перегрузке нельзя незаметно подменять ответ модели тестовым JSON.

Измеряют полную задержку от нажатия до карточки. Холодный запуск фиксируют отдельно от прогретого; после серии осмотров считают медиану и p95. Численный целевой предел согласуют по сценарию работы инженера и измеренной сети. Одна быстрая повторная фотография не является гарантией времени ответа.

Для серверной приёмки проверяют запуск задач после разрешённого перезапуска, восстановление SQLite из копии, обновление сертификата, освобождение GPU, журнал ошибок и отсутствие отправки кадров во внешнюю модель. Перезапуск всего рабочего сервера требует согласованного окна; в текущей проверке подтверждены регистрация и работа задач, а не перезагрузка Windows.

## Приёмка визуальной модели

До измерения качества фиксируют неизменяемую проверочную выборку, версии модели и промпта, условия съёмки и протокол разметки. Результаты группируют по экземпляру насоса, сессии и виду дефекта. Независимая проверка должна включать исправные видимые узлы, подтверждённые дефекты, похожие загрязнения и непригодные кадры.

Отдельно измеряют попадание рамки в нужный компонент, распознавание видимого признака, долю отказов от оценки и пропуски подтверждённых дефектов. Ответ `unusable` не засчитывают автоматически как правильный диагноз. Для положительных результатов считают ложные тревоги; для отрицательных — пропуски. После этого согласуют допустимую долю ошибок и область применения. У текущей Qwen3-VL численной метрики точности на насосах пока нет.

## Приёмка табличной модели

Выбор гиперпараметров и порогов выполняют на обучении и валидации. Итоговую проверку открывают после фиксации решения. Рядом с метриками указывают число машин, сессий и подтверждённых эпизодов каждого состояния. Если тест уже использовали для подбора решения, его статус меняют на валидационный и собирают новую независимую проверку.

Для каждого отказа интересны пропуски, ложные тревоги и качество при реальной распространённости событий. Нельзя принять модель только по общей accuracy, когда она игнорирует опасный класс. Показатели открытого лабораторного стенда не являются оценкой конкретного завода. Для промышленного пилота сначала нужен наблюдательный режим, в котором выводы сверяют с инженером и не используют как команды оборудованию.

## План команды на ближайшие два дня

**Участник 1 — вебка и интеграция.** Проверить телефоны, провести связку QR → выбранный насос → кадр → результат → запись. Добавить отдельное хранение реальных наблюдений и доказательств, сохранив режим демонстрации. На выходе — демонстрационный сценарий, спецификация API и запись успешной проверки на двух устройствах.

**Участник 2 — данные и модели.** Подтвердить исполнение насоса и доступные измерения, разметить небольшую независимую фотосерию, подготовить словарь каналов. Повторить фиксированный эксперимент по плану без подбора по тесту. На выходе — каталог данных, протокол разметки, таблица ошибок и список условий, при которых модель отказывается от оценки.

**Участник 3 — Android и презентация.** Проверить WebView с HTTP-аутентификацией и разрешениями камеры. Подготовить показ проблемы, архитектуры, живого осмотра и известных ограничений. На выходе — проверенная оболочка, презентация с разграничением фактически работающих функций и следующих этапов.

После хакатона отдельными этапами идут импорт SCADA, версионирование профилей, подтверждение диагнозов инженером, многопользовательские роли, испытания на разных агрегатах и оценка остаточного ресурса по истории. Объём оценивают после получения данных; произвольный срок «до отказа» в карточку не добавляют.
