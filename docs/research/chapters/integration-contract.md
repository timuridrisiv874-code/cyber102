# Интеграция паспорта датчиков и визуального осмотра

Cyber102 уже объединяет интерфейс камеры, локальное зрение и диагностику по правилам на одном сервере. Следующий этап — связать эти части по идентификатору оборудования и времени наблюдения. Паспорт, реальный кадр и фактические показания должны относиться к одному насосу. Ни совпадение названия модели, ни выбранный демонстрационный сценарий сами по себе этого не подтверждают.

## Текущее состояние

| Компонент | Реализовано | Граница результата |
| --- | --- | --- |
| Паспорт | Поиск `P-102`, QR, SQLite | Данные демонстрационные; заводской паспорт не загружен |
| Правила | 12 связок, объяснения, 14 сценариев | Входы нормализованы заранее; расчёта трендов из SCADA ещё нет |
| Зрение | JPEG/PNG, локальная Qwen3-VL 8B, рамка и наблюдение | Один видимый компонент; серийный номер не подтверждается |
| История | Сохранение сценария, заметки, признаков и выводов | Кадры и результаты `/analyze` пока не записываются в журнал |
| Обучение | Измерен CatBoost на UCI; подготовлен конвейер с опциональным AutoGluon | Заводского классификатора и расчёта остаточного ресурса нет |

Работающая реализация описана в [документе БД](../../architecture/database.md) и [контракте зрения](../../architecture/vision.md). В этой главе ниже предложено расширение. Новые поля и процедуры не следует считать уже поддерживаемыми HTTP API.

## Целевой путь одного осмотра

1. Оператор открывает QR, проверяет серийный номер и фотографию шильдика. Сервер выдаёт паспорт и перечень компонентов. В ручном режиме оператор явно подтверждает выбор насоса.
2. Приложение создаёт `inspection_id` и время начала. Кадр получает отдельный `frame_id`, размер изображения и связь с выбранным компонентом. В интерфейсе видно, что идентификатор выбран оператором, а не распознан моделью.
3. Сервер получает доступную телеметрию этого насоса. В ответе сохраняются исходное время измерения, время получения и признак качества. Для каждого канала применяется согласованное окно актуальности.
4. Модуль признаков проверяет единицы, полноту окна, режим нагрузки, базовую линию и качество. Только после этого он формирует `rising`, `normal` или число для существующего движка правил. Неизвестный признак остаётся неизвестным.
5. Зрение возвращает наблюдение и область кадра. Оператор может подтвердить или исправить наблюдение. Сырой ответ модели и подтверждение инженера — разные сущности.
6. Движок возвращает предварительные гипотезы с использованными измерениями, версиями профиля и правил. Карточка показывает отдельно увиденное на фото, данные датчиков и вывод.
7. Сохранение создаёт неизменяемый снимок доказательств. Последующее исправление добавляет новую версию с автором и причиной. Обслуживание, замена и снятие предупреждения становятся отдельными событиями.

## Контракт одного измерения

В OPC UA `DataValue` связывает значение, статус и временные метки; исходная метка времени не равна времени получения сервером. Эти сведения нужно сохранять при импорте. Статус ошибки нельзя преобразовывать в нормальное значение. [I01 — OPC Foundation DataValue](https://reference.opcfoundation.org/specs/OPC-10000-4/7.11)

В [telemetry-example.json](../schemas/telemetry-example.json) приведён вымышленный пример одного агрегированного измерения. [telemetry-schema.json](../schemas/telemetry-schema.json) проверяет форму документа. Она не удостоверяет исправность датчика, синхронизацию часов или инженерную применимость показателя.

| Группа | Обязательное содержание | Проверка импортера |
| --- | --- | --- |
| Идентичность | `serial`, `sensor_id`, `component_id` | Привязка к паспорту и месту установки |
| Время | `source_timestamp`, `received_at` | Часовой пояс, порядок, допустимое запаздывание |
| Величина | `quantity`, `value`, `unit` | Единицы и допустимый физический диапазон |
| Качество | `quality`, `source` | Плохое качество исключается из подтверждений |
| Окно | Начало, конец, частота и число отсчётов | Достаточность данных для заявленного признака |
| Режим | Скорость, нагрузка, состояние агрегата | Сопоставимость с базовой линией |

Строка `MPa` должна означать давление, а `mm/s` — скорость вибрации. Нельзя сравнивать ускорение в `g` со скоростью в `mm/s`, RMS с peak, либо избыточное давление с абсолютным без явного преобразования. OPC UA предусматривает представление инженерных единиц; в импорте Cyber102 сохраняем исходную единицу и версию преобразования. [I02 — OPC Foundation EUInformation](https://reference.opcfoundation.org/specs/OPC-10000-8/5.6.4)

Для давления дополнительно согласуют тип датчика и точку отбора. Для вибрации — ось, крепление, полосу, частоту дискретизации, фильтрацию и способ расчёта. Один RMS из SCADA не восстанавливает высокочастотный спектр. Выбор частоты измерений связан с полосой и антиалиасинговым фильтром измерительного тракта. [I03 — NI об измерении сигналов](https://www.ni.com/en/shop/data-acquisition/measurement-fundamentals/analog-fundamentals/acquiring-an-analog-signal--bandwidth--nyquist-sampling-theorem-.html)

## Преобразование измерений в признаки

Конфигурация профиля должна задавать `profile_version`, применимые режимы, состав каналов, окно расчёта, минимальную полноту и согласованную базовую линию. До согласования эти параметры не получают эксплуатационных значений по умолчанию.

**Рост.** Для каждого показателя задают метод оценки изменения, величину отклонения и длительность его сохранения. Пуск, переключение задвижки и изменение оборотов обрабатывают как отдельные режимы. Профиль должен описывать, когда предупреждение снимается, чтобы результат не переключался на каждом шумовом отсчёте.

**Норма.** Это результат проверки диапазона, качества и режима. Отсутствие записи, отключённый датчик или неопределённое распознавание дают `unknown`, а не `normal`. В текущем JSON правила используют отсутствие ключа для неизвестного входа; в хранилище полезно дополнительно сохранять причину отсутствия.

**Снижение КПД.** Для правила «15%» фиксируют относительное изменение: `(eta_ref − eta_current) / eta_ref × 100`. Например, переход с 80% до 68% означает относительное снижение на 15% и снижение на 12 процентных пунктов. Это арифметический пример, не характеристика данного насоса. Сравнение требует одного определения КПД и сопоставимого режима. КПД насоса и КПД агрегата с электродвигателем используют разные входные мощности. [I06 — KSB Pump efficiency](https://www.ksb.com/en-global/centrifugal-pump-lexicon/article/pump-efficiency-1116510)

**Счётчик наработки.** Сохраняют предыдущую и текущую наработку, дату установки счётчика, сбросы и события обслуживания. Пересечение 8 000 часов и «ТО уже выполнено на 8 005» — разные события. Постоянное напоминание должно опираться на последнюю подтверждённую операцию обслуживания, а не только на сравнение двух значений.

**Разные приборы давления.** Перед сравнением фиксируют одинаковый режим и сопоставимое время. На аналоговом манометре чтение стрелки требует геометрии шкалы; одного OCR цифр недостаточно. Вопрос, какой прибор ошибается, не решается фактом расхождения. Для `SCADA = 0` относительная формула не определена; приложение должно показать невозможность сравнения.

Схема Draft 2020-12 проверяет допустимые типы, соответствие величины единице, обязательные поля и отсутствие числа при `missing`. При разработке импортера отдельно проверяют порядок времён, `sample_count <= expected_sample_count`, границы частотной полосы, длину окна и частоту, существование канала в паспорте и актуальность данных. Для `bad` и `uncertain` исходное число может сохраняться как свидетельство, но не подтверждает правило. Пример с 68°C полностью синтетический и не задаёт норму температуры. [I07 — JSON Schema](https://json-schema.org/draft/2020-12)

## Хранение и воспроизводимость

Для одного диагностического результата сохраняют `inspection_id`, идентификатор оборудования, время, версии профиля, правил, модели, исходные признаки, пропуски, выводы и подтверждение оператора. Рамка хранится вместе с геометрией именно того кадра, на котором получена. Текст рекомендации имеет версию; изменение документа производителя не должно задним числом менять старую запись.

SQLite подходит текущему объёму паспортов и осмотров. Режим WAL позволяет организовать совместное чтение и запись, но не превращает файл в распределённую базу; ограничения режима нужно учитывать при переносе на сетевой диск. Для резервирования работающей базы используем Online Backup API, а затем проверяем восстановление отдельной копии. [I04 — SQLite Backup API](https://sqlite.org/backup.html) · [I05 — SQLite WAL](https://www.sqlite.org/wal.html)

Поток сырых измерений можно вынести в отдельное хранилище после оценки числа датчиков, частоты, срока хранения и запросов. При выборе ClickHouse сначала проверяют схему ключей, поздние измерения, дубликаты и объём агрегатов на реальной выгрузке. Сам факт наличия RTX 3090 не требует распределённой БД: GPU выполняет визуальную модель, а не операции SQLite.

## Границы промышленного контура

Сейчас публичный стенд на 3090 доступен по паролю. Заводское размещение предполагает согласованный внутренний HTTPS-адрес, доступ операторов к разрешённым агрегатам, локальные веса и ограничения исходящих соединений. В качестве отдельной проверки выполняют осмотр при отключённом внешнем интернете и наблюдают сетевые обращения. Название переменной «local» само по себе не доказывает изоляцию.

Для заводского ввода нужны роли оператора и инженера, учёт авторства правок, политика хранения кадров, резервирование, журнал версий и проверенный способ восстановления. Текущее приложение не управляет PLC, защитами или приводом. Рекомендации не являются автоматическими командами остановки либо ремонта.
