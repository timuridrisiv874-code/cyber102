# Запрос данных для пилота Cyber102

Этот шаблон предназначен для передачи заказчику после согласования с командой. Он описывает минимальные сведения, которые позволят связать фото, датчики и состояние конкретного насоса. Сам документ никому автоматически не отправляется.

## Оборудование и регламенты

Нужны фотография шильдика, точное обозначение и исполнение насоса, изготовитель, заводской номер, двигатель, тип муфты, уплотнения, подшипников и смазки. Просим действующие паспорта, кривые рабочих характеристик, регламент обслуживания и применимые пороги. Для каждого документа полезны редакция и дата. Маркировка из карточки продавца недостаточна для назначения момента затяжки, масла и межремонтного интервала.

Нужно определить один агрегат для показа и несколько разных агрегатов для последующей оценки переноса модели. Фотографии одной машины с разных ракурсов не заменяют несколько независимых машин. Если доступен только один насос, результат пилота явно ограничивается этим насосом и условиями съёмки.

## Телеметрия

Просим небольшой обезличенный фрагмент выгрузки, словарь каналов и описание формата. Для каждого канала указывают единицы, место установки, ось, частоту измерения, калибровку, время источника и признак качества. Особо нужны скорость вращения, режим нагрузки и события пуска/останова. Для спектральной диагностики следует выяснить, доступны ли исходные временные сигналы либо только готовые агрегаты.

Период должен включать подтверждённую исправную работу и доступные эпизоды неисправности до и после обслуживания. Объём определяется частотой данных, количеством машин и наличием подтверждений. Несколько суток нормальных измерений не дают примеров редких отказов автоматически.

## Фото и подтверждения дефектов

Просим разрешённые фотографии видимых компонентов с привязкой к серийному номеру, времени и сессии съёмки. Нужны общий вид, шильдик, зона дефекта и контрольный ракурс. Следует указать, можно ли хранить исходные кадры и производные разметки, кто имеет доступ и требуется ли удалить лица или служебные обозначения.

Метка состояния должна опираться на осмотр или документированную операцию обслуживания. Для каждого эпизода указывают компонент, наблюдение, предполагаемую причину, способ подтверждения, дату ремонта и результат после него. «Модель увидела коррозию» и «инженер подтвердил коррозию» хранят отдельно. Неуверенные случаи полезны, если они прямо обозначены как неизвестные.

## Эксплуатационная среда

Нужно согласовать адрес и сертификат внутри сети, доступные телефоны и версии ОС, способ авторизации, наличие Android WebView, правила работы с камерой, допустимую задержку и условия без интернета. Для сервера — ОС, GPU, память, свободный диск, разрешённые пакеты, порядок резервирования и ответственный за восстановление.

Пилот не должен требовать отключения защит, снятия кожухов работающего оборудования или создания неисправностей. Съёмка и измерения выполняются персоналом площадки в разрешённых точках. Команда использует уже доступные безопасные наблюдения и результаты обслуживания.

## Что команда передаст в ответ

Согласованный перечень проверяемых состояний, схему импорта, карточки правил, протокол разметки, состав независимой проверки, отчёт по ошибкам и воспроизводимый выпуск приложения. Значения порогов и действие при предупреждении утверждаются отдельно от качества интерфейса. Для прогноза остаточного ресурса дополнительно понадобится история отказов, замен и наработки; одного текущего кадра для этого недостаточно.
