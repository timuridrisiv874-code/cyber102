# Камера Cyber102 по локальному Wi‑Fi

Это инструкция для следующего этапа. Сейчас сервер удалённый и телефоны работают через внешний HTTPS. При осмотре конфигурации сервера наблюдался локальный адрес `192.168.31.19`; перед переносом на площадку адрес проверяют заново. Внешняя демонстрация открывается по адресу [Cyber102 HTTPS](https://cyber102.94.41.87.102.sslip.io/). В обоих случаях анализ происходит на сервере. При открытии внешнего адреса без локальной DNS-записи кадр может пройти через публичный маршрут. Для изолированного теста используйте описанный ниже локальный маршрут.

## Настройка адреса

1. Подключите телефон к Wi‑Fi, из которого доступен сервер `192.168.31.19` по TCP 443. Закрепите адрес сервера в DHCP, если его выдал роутер.
2. В DNS этой сети добавьте локальную A-запись `cyber102.94.41.87.102.sslip.io → 192.168.31.19`. Телефоны и ноутбук должны использовать этот DNS. Проверьте, что DNS-фильтры роутера и настройки VPN или частного DNS на клиенте позволяют получить локальный ответ. Если роутер фильтрует возврат частного IP для публичного домена, настройте исключение только для этого имени.
3. Открывайте прежнее имя по HTTPS. Caddy выбирает сертификат по имени, поэтому имеющийся действующий сертификат подходит и при обращении к локальному IP через это имя. Прямой HTTP по IP не даёт странице безопасный контекст, необходимый камере. [HTTPS Caddy](https://caddyserver.com/docs/automatic-https) · [Доступ к камере в W3C](https://www.w3.org/TR/mediacapture-streams/#dom-mediadevices-getusermedia)

Эта DNS-запись и настройки на телефонах ещё не подтверждены. Службы веб-API `8102` и модели `11436` слушают loopback. С устройств используется HTTPS-порт Caddy.

## Проверка с ноутбука

Из той же Wi‑Fi сети проверьте DNS и отдельно проверьте, что Caddy отвечает на локальном IP с правильным TLS-именем. `curl --user cyber102` запросит пароль интерактивно.

```bash
nslookup cyber102.94.41.87.102.sslip.io
curl --fail --show-error --user cyber102 \
  --resolve cyber102.94.41.87.102.sslip.io:443:192.168.31.19 \
  https://cyber102.94.41.87.102.sslip.io/api/health
```

DNS должен вернуть `192.168.31.19`. Запрос с `--resolve` проверяет маршрут напрямую и оставляет проверку сертификата включённой. Затем повторите запрос без `--resolve` для проверки обычного DNS. Этот тест подтверждает доступность веб-приложения. Чтобы подтвердить GPU-путь, отправьте кадр через экран камеры и проверьте модель в результате анализа.

## Проверка с телефонов

1. **iPhone.** Откройте тот же HTTPS-адрес в Safari, войдите и выберите «Осмотр камерой». Разрешите камеру, наведите её на разрешённый пример оборудования и нажмите «Проверить кадр».
2. **Android.** Повторите в Chrome и в сборке Android WebView. Оболочка должна обработать вход по HTTP-аутентификации и выдать `RESOURCE_VIDEO_CAPTURE` для доверенного origin после разрешения камеры в Android. [Разрешения WebView](https://developer.android.com/reference/android/webkit/PermissionRequest)
3. На обоих телефонах включите «Видеопроверка», дождитесь нескольких результатов и проверьте карточку на последнем проверенном кадре. Нажмите «Остановить проверку», затем повторите запуск. Убедитесь, что при уходе страницы в фон камера останавливается.
4. Для проверки автономного маршрута используйте тестовую сеть с отключённым WAN, сохранив локальное соединение. На телефоне отключите мобильные данные. Заново откройте HTTPS-страницу и повторите вход, одиночный кадр и видеопроверку. Зафиксируйте адрес DNS, устройство, браузер, время и результат. В автономном контуре следите за сроком действия сертификата. Долгосрочную схему его выпуска или обновления согласовывают с владельцем сети.

Подробнее о Windows-службах и внешнем HTTPS см. в [инструкции развёртывания](deployment.md).
