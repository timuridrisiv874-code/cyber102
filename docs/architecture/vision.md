# Локальная проверка камеры Cyber102

Экран «Осмотр камерой» показывает предварительное наблюдение, карточку узла и рамку на проверенном кадре. Для стенда выбрана `Qwen/Qwen3-VL-4B-Instruct` в отдельном GPU-процессе на RTX 3090 Ti. Выбор основан на сравнении с InternVL3.5-2B на 53 изображениях организаторов; это исследовательская визуальная проверка, без экспертной разметки. Встроенные примеры используют подготовленные ответы для репетиции интерфейса. [Протокол сравнения](../ml/vlm-comparison-2026-11-13.json) · [Карточка Qwen3-VL-4B](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct)

## Один кадр и видеопроверка

В режиме «Один кадр» пользователь включает камеру, наводит её на узел и нажимает «Проверить кадр». Камера фиксирует изображение, а интерфейс показывает ответ анализа на этом изображении.

В режиме «Видеопроверка» браузер оставляет предпросмотр камеры открытым и отправляет отдельные JPEG. По умолчанию между началами запросов проходит не менее 5 секунд, также доступны интервалы 2 и 10 секунд. Следующий кадр отправляется только после ответа на предыдущий. При задержке модели фактическая частота снижается. Рамка относится к последнему проверенному снимку, показанному отдельно от живого предпросмотра. Модель анализирует каждый снимок независимо. При проверке по интервалу интерфейс показывает число проверенных кадров. Для фото применяется стандартный профиль автоматически.

Кнопка «Остановить проверку» отменяет ожидание ответа в браузере. На сервере уже начатый инференс может завершиться самостоятельно. При ошибке цикл останавливается, а при уходе страницы в фон камера освобождается. Браузер запрашивает видеодорожку камеры.

## Передача и проверка кадра

Браузер отправляет один `file` в `multipart/form-data` на `POST /analyze` того же HTTPS-адреса. Приложение принимает JPEG или PNG до 3 МиБ и 8 мегапикселей. Pillow корректирует ориентацию и ограничивает длинную сторону 1280 пикселями. При backend `internvl3` веб-API отправляет нормализованный кадр на `http://127.0.0.1:11436/analyze`. Внутренний запрос содержит только JSON с изображением в Base64. Пригодные фото и ответы сохраняются в `analysis_evidence` для последующего подтверждения осмотра: несохранённые в журнал свидетельства ограничены двумя часами и 64 записями. История подтверждённых осмотров хранится отдельно.

GPU-процесс запрашивает у выбранной VLM наблюдение по одному видимому компоненту. Приложение проверяет точный набор полей, допустимые классы, границы рамки и идентичность модели. Координаты ответа преобразуются в доли ширины и высоты снимка. Ответ сохраняет существующие поля `source`, `model`, `status` и, для применимого результата, карточку с рамкой. При недоступности модели API возвращает ошибку. Совместимое имя backend `internvl3` обозначает этот локальный HTTP-контракт, а конкретный снимок задаётся общим файлом `var/vlm-model.txt`: `qwen3_vl_4b` или `internvl3_5`. Выбор Ollama выполняется явно через отдельную конфигурацию. [Локальный GPU-процесс](../../vision_runtime/README.md)

| Результат API | Что видит пользователь |
| --- | --- |
| `defect` | Возможная коррозия, следы жидкости или видимое повреждение. Рамка выделяет выбранный компонент. |
| `clear` | Явных внешних признаков не замечено. Карточка предлагает сверить состояние с датчиками и историей обслуживания. |
| `unusable` | Модель не уверена или не распознала подходящий узел. Экран предлагает повторить съёмку. |
| `503` | Модель занята, недоступна либо вернула ответ, который приложение не смогло обработать. |

Поддерживаются корпус насоса, электродвигатель, муфта или кожух, трубопровод или фланец, подшипниковый узел, запорная арматура и клеммная коробка. Серийный номер, остаточный ресурс и сроки обслуживания берут из паспорта и истории. Для оценки кавитации, внутреннего износа, перегрева и электрических параметров нужны измерения и инженерная проверка.

## Стенд и проверка результата

На Windows GPU-процесс запускается заданием `Cyber102InternVL`, веб-приложение — заданием `Cyber102Web`. Для проверки камеры с телефона используется HTTPS. Процедура отдельной проверки внутри Wi‑Fi описана в [инструкции по локальной сети](../operations/local-network.md).

### Исходная проверка Qwen3-VL

Прежний `qwen3-vl:8b` в Ollama ответил через публичный HTTPS на двух фото насосов и белом кадре. Фото вернули предварительный признак коррозии с рамкой, белый кадр вернул `unusable`. Первый запрос с загрузкой занял около 24 секунд. Повторные серверные вызовы занимали 1,1–1,6 секунды. Это проверка доступности и формата ответа. [Фото Warman и лицензия](https://commons.wikimedia.org/wiki/File:Warman_centrifugal_pump.jpg)

### Проверка InternVL3

InternVL3-2B-hf прошла 10 запросов на пяти тестовых кадрах: два синтетических насоса, открытое неразмеченное фото Warman, белый кадр и изображение с текстом. Все ответы прошли проверку формата; нерелевантные кадры получили `unusable`. Во втором проходе медиана составила 4,391 с. Это функциональная проверка, точность классов и рамок на заводской выборке ещё не измерена. [Исходные результаты](../ml/internvl3-smoke-report.json)

Браузерные тесты с синтетической камерой проверяют отправку JPEG, последовательные запросы, остановку и уход в фон. Дополнительно Chromium и WebKit получили настоящие ответы GPU через публичный HTTPS. [Протокол](../ml/internvl3-browser-report.json) Приёмка на физических iPhone и Android остаётся отдельной проверкой команды. Сейчас сервер удалённый: кадры идут по HTTPS через интернет к серверу команды. Локальная сеть на площадке запланирована позднее.


## Совместный обзор видео

`POST /api/video-review` принимает JSON с `frames` (1–8 изображений JPEG/PNG в Base64 и возрастающие `timestampSeconds`) и длительностью ролика `durationSeconds` до 120 секунд. Браузер отбирает равномерные кадры из локального видео и уменьшает их до отправки. API проверяет размер, декодирование, таймкоды и источник запроса, обращается только к loopback-процессу `/analyze-video`.

После загрузки ролика основная кнопка «Проверить всё видео» отправляет восемь кадров одним запросом, независимо от текущего положения плеера. На GPU Qwen обрабатывает последовательность небольшими группами. Выход содержит `summary`, `observations`, `model`, `revision`, `clipDurationSeconds` и время обработки `durationSeconds`. При включённой перепроверке Qwen дополнительно ищет разрывы металла и повреждения проводки и проверяет предложенные области крупным планом. Массив `defectDetails` может содержать несколько рамок на один момент. Каждая область имеет координаты 0–1000 относительно исходного кадра. Результат описывает выбранные кадры. Если есть пригодный кадр, сервер возвращает `representativeFrame.analysisId`. По кнопке «Оформить видеоосмотр» инженер может сохранить сводку, наблюдения с таймкодами и один опорный JPEG в журнал. [Проверка сохранения и повторного открытия](../../tests/browser/video-history-smoke.cjs)

Запросы фото и видео проходят через общую очередь одного GPU. Отмена исключает устаревший ответ, но не гарантирует мгновенного прерывания уже начатой генерации: слот остаётся занят до её фактического завершения. Старые синхронные клиенты получают `vision_busy`, если очередь уже занята.

В интерфейсе каждая серия соседних кадров с одинаковым узлом и признаком получает одну карточку с таймкодами. Если признак появляется снова после другого наблюдения, создаётся отдельная карточка. Все найденные эпизоды показаны сразу. По кнопке «Уточнить кадр» можно открыть отдельное фотоисследование выбранного момента, сохранив сводку ролика на странице. Когда все выбранные кадры пригодны и в обоих проходах нет находок, достаточно одной короткой сводки. Для кадров без оценки есть отдельное состояние.

Qwen прошла техническую проверку joint8 за 57,08 с с пиком занятой видеопамяти PyTorch 13,76 GiB. Последовательность собрана из восьми разных фото и не проверяет движение. Все восемь рамок в ней оказались одинаковыми и широкими; этот результат не подтверждает точность AR-локализации. Следующий этап — реальные ролики с разметкой выбранных кадров и проверка области каждого найденного признака.

## Очередь нескольких пользователей

Веб-клиент проверяет `vision.queue.enabled` в `/api/capabilities` и отправляет `Prefer: respond-async` на прежние `/analyze` и `/api/video-review`. Ответ `202` содержит `job`: идентификатор, состояние и позицию среди ожидающих. Проверка входных файлов выполняется до постановки задания; HTTP-соединение не удерживается всё время анализа. Один исполнитель обслуживает фото и видео в порядке поступления.

`GET /api/analysis-jobs/{id}` возвращает состояние и `job.result` после успеха. `POST /api/analysis-jobs/{id}/cancel` отменяет ожидание. Заголовок `X-Analysis-Client` — случайный секрет браузерной сессии; чужие задания не раскрываются. `X-Analysis-Request` задаёт идемпотентность отправки: повтор того же запроса не создаёт новый анализ, другой файл под тем же ключом отклоняется. Отмена по `/api/analysis-jobs/by-request/{requestId}/cancel` закрывает случай, когда браузер ещё не получил идентификатор задания.

Ограничения одного процесса: одно выполняемое задание, до восьми ожидающих, до двух незавершённых от одной браузерной сессии, не более 64 МиБ входных данных очереди. Ожидание ограничено десятью минутами. Завершённые результаты доступны пять минут; общий реестр ограничен 64 заданиями. Эти ограничения защищают ресурсы и обеспечивают простую справедливость между браузерами; секрет сессии не является отдельной учётной записью пользователя.

При отмене ожидающего задания его кадры освобождаются сразу. Выполняемое задание переходит в `cancelling`; следующий анализ начнётся после освобождения исполнителя. Ответ отменённого задания не сохраняется как новый результат фото. Очередь находится в памяти: после перезапуска сервера незавершённый запрос нужно отправить снова. Для нескольких процессов API или нескольких GPU понадобится внешний диспетчер; увеличение числа веб-процессов с отдельными очередями не увеличивает безопасную пропускную способность этого стенда.
