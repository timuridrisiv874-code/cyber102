# База данных Cyber102

Cyber102 хранит паспорт насоса, демонстрационные сценарии диагностики и историю сохранённых осмотров в SQLite. База открывается сервером Python с локального диска. Телефон обращается к HTTP API, а на площадке открывает его вместе с веб-интерфейсом по одному HTTPS-адресу внутри локальной сети. На RTX 3090 Ti уже работает локальный модуль компьютерного зрения Qwen3-VL через отдельный `/analyze`. По команде инженера сохраняются результат модели, проверенный кадр и происхождение показаний. Для SQLite и расчёта правил достаточно CPU.

## Таблицы и связи

| Таблица | Ключи | Данные |
| --- | --- | --- |
| `pumps` | `serial` — первичный ключ | `passport_json` содержит модель, наименование, сведения об обслуживании, происхождение данных и пороги диагностики. |
| `inspections` | `(serial, id)` — первичный ключ. `serial` ссылается на `pumps.serial` | `label` — название сценария. `telemetry_json`, `vision_json`, `zones_json` — входные признаки и зоны подсветки. `source` — источник. `captured_at` — время наблюдения, если оно задано. |
| `inspection_records` | `id` — UUID записи. `serial` ссылается на `pumps.serial`. Пара `(serial, request_id)` уникальна при заданном `request_id` | `scenario_id` хранит идентификатор выбранного сценария, если он задан. `telemetry_json`, `vision_json`, `findings_json` — сохранённые входные данные и выводы. `note` — заметка до 1 000 символов. `captured_at` — время сохранения в UTC. |
| `analysis_evidence` | UUID анализа | Проверенный JPEG, SHA-256, результат и признак сохранения в журнал. У видео результат содержит сводку и таймкоды. |
| `inspection_closeups`, `inspection_work` | Ссылка на запись осмотра | Точка на общем виде, крупный план с отметками замера, действие инженера, дата и фото после работ. |

Паспорт связан со сценариями и сохранёнными осмотрами через `serial`. Сервер загружает признаки из выбранного сценария и применяет пороги из паспорта. При сохранении осмотра входные данные и выводы фиксируются на момент записи. Это позволяет показать, какие признаки привели к выводу, даже если сценарий или правила впоследствии изменятся. В `inspections` поле `captured_at` относится к наблюдению, а в `inspection_records` показывает, когда оператор сохранил результат. Повтор с тем же `request_id` возвращает прежнюю запись. Если сценарий, признаки или заметка изменились, сервер сообщает о конфликте.

## Данные демо и данные завода

При первом запуске сервер создаёт `var/cyber102.sqlite3` и добавляет демонстрационный паспорт `P-102` с исходным названием насоса «Д 160-1126» и 14 сценариев из `server/demo_data.py`. Нормальный сценарий, 12 диагностических связок и пример с несколькими выводами используют подготовленные признаки. `captured_at` в этих сценариях пуст. Пороговые наработки 4 000, 8 000 и 16 000 часов относятся к демонстрационному паспорту.

| Данные | Прототип | Для подключения завода |
| --- | --- | --- |
| Паспорт | Модель, серийный номер и демонстрационные интервалы | Заводские идентификаторы, характеристики компонентов, пороги по режимам, сроки службы и регламент ТО. |
| Телеметрия | Готовые состояния `rising`, `falling`, `normal`, `high`, `slightly_high` и численные отклонения | Ряды измерений с `serial`, `sensor_id`, временем в UTC, значением, единицей измерения и признаком качества. Для трендов нужны базовый уровень, окно сравнения и режим работы. |
| Визуальные признаки | Сценарии используют синтетические флаги; `/analyze` отдельно возвращает реальное наблюдение локальной модели | Результат локального распознавания с временем съёмки, идентификатором кадра и, при наличии, уверенностью модели. Для давления нужна единица, совпадающая с данными SCADA. |
| Подсветка | Зоны на схеме насоса и рамка на конкретном проверенном кадре | Проверка точности локализации на полевых изображениях. |
| История | Сохранённые кадры, результат диагностики, крупный план, действие инженера, дата и фото после | Даты установки, обслуживания и замены отдельных компонентов, подтверждения инженера и данные для расчёта остаточного ресурса. |

Неизвестное измерение передаётся без значения. `false` и `normal` используются для подтверждённого отсутствия признака или подтверждённой нормы. Диагностика выдаёт предварительные выводы для проверки инженером. Пределы и рекомендации для эксплуатации сверяются с паспортом и процедурами объекта.

## Обмен данными через API

| Запрос | Результат |
| --- | --- |
| `GET /api/scenarios?serial=P-102` | Паспорт, список идентификаторов и названий сценариев, доступность QR. |
| `GET /api/diagnose?serial=P-102&scenario=pressure_mismatch` | Паспорт, сценарий, признаки, зоны и вычисленные выводы. |
| `POST /api/diagnose` | Принимает `serial`, `telemetry` и `vision`. Рассчитывает выводы в памяти. |
| `GET /api/history?serial=P-102` | Объект `records` с сохранёнными осмотрами в порядке от новых к старым. |
| `POST /api/history` | Принимает `serial`, `scenarioId`, `note` и `requestId`. Сервер берёт признаки из сохранённого сценария и рассчитывает выводы перед записью. Возвращает `record` и `created`. |
| `POST /api/video-review` | Совместный разбор выбранных кадров с таймкодами. При пригодном результате возвращает опорный кадр с серверным `analysisId`. |
| `POST /api/inspections/preview` и `POST /api/inspections` | Предварительный осмотр и запись в журнал по `analysisId`. Для видео сохраняются сводка, проверенные таймкоды и один опорный JPEG. |
| `POST /api/history/{id}/work` | Регистрация проверки или замены с датой и необязательной фотографией после работ. |

Для повторной отправки того же осмотра клиент использует исходный `requestId`. Для нового осмотра клиент создаёт новый `requestId`. История объединяет записи с камеры, загруженных файлов и учебных сценариев. Входные признаки, отправленные в `POST /api/diagnose`, используются только для расчёта ответа.

## Запуск и SQL

Из корня репозитория выполните `python3 -m server.app`. Сервер создаст базу при запуске. Для отдельного прогона можно указать `--database /путь/к/демо.sqlite3`. Используйте SQLite CLI в режиме чтения для просмотра данных.

```bash
sqlite3 -readonly var/cyber102.sqlite3
```

```sql
-- Паспорт и перечень сценариев одного насоса
SELECT p.serial,
       json_extract(p.passport_json, '$.model') AS model,
       i.id,
       i.label,
       i.source
FROM pumps AS p
JOIN inspections AS i ON i.serial = p.serial
WHERE p.serial = 'P-102'
ORDER BY i.rowid;

-- Входные признаки для сценария расхождения давления
SELECT json_extract(telemetry_json, '$.discharge_pressure') AS scada_mpa,
       json_extract(vision_json, '$.gauge_pressure') AS gauge_mpa
FROM inspections
WHERE serial = 'P-102' AND id = 'pressure_mismatch';

-- Последние сохранённые осмотры
SELECT id,
       captured_at,
       scenario_id,
       json_array_length(findings_json) AS finding_count,
       note
FROM inspection_records
WHERE serial = 'P-102'
ORDER BY captured_at DESC, rowid DESC
LIMIT 10;
```

## Выбор хранилища

Для прототипа SQLite позволяет держать приложение и данные на одной машине. База создаётся из кода, помещается в один файл и не требует отдельного процесса. Операторы работают через API, поэтому файл базы остаётся на диске сервера. Для резервной копии работающего приложения используйте команду SQLite `.backup` или API резервного копирования. [SQLite о выборе хранилища](https://www.sqlite.org/whentouse.html)

Если поступит поток телеметрии, оценим частоту записи, глубину хранения и запросы по времени. Для потоковых рядов можно выделить локальную таблицу ClickHouse с ключом сортировки `(serial, sensor_id, ts)` и хранить в ней сырые измерения. Сервис диагностики будет получать агрегаты за нужное окно и передавать в движок правил тот же контракт `telemetry`. Паспорта и запись истории останутся в SQLite, пока объём и частота записи позволяют выполнять эти операции на одной машине. [ClickHouse для временных рядов](https://clickhouse.com/docs/guides/use-cases/real-time-analytics/time-series)

## Инженерное уточнение

В официальном руководстве семейства указано исполнение Д160–112б (кириллическая «б»). Название демопаспорта не подтверждает исполнение реального агрегата. Сверьте шильдик и паспорт перед переносом характеристик. Источники, контракт телеметрии и план подключения приведены в [инженерном пакете](../research/README.md).
