# Задачи Тимура

## День 1 — проверить текущий прототип

Уточнение заказчика: обход оценивает внешние признаки; снятые внутренние детали — дополнительный режим. Полностью автономный телефон не требуется: серверное распознавание и связь по внутреннему Wi-Fi допустимы. На этом этапе используем удалённую 3090, а телеметрию проигрываем из предоставленных баз.

Перед показом открыть [паспорта](https://cyber102.94.41.87.102.sslip.io/documents.html) и [эмулятор](https://cyber102.94.41.87.102.sslip.io/telemetry.html). В паспортах — реальные винтовые насосы AMS, в старом сценарии P-102 — центробежный демо-насос. Показания из примеров не привязаны к паспортам: для интеграции нужны соответствие серийников тегам сервера ввода/вывода и адреса OPC UA/Modbus. Демо-пороги и регламент ТО нельзя автоматически переносить в новый тип оборудования.

1. На удалённом HTTPS-стенде открыть паспорт `P-102`, показать сценарий с несколькими выводами и запись с заметкой в журнале. Команды для локальной проверки API и тестов есть в [чек-листе](CHECKLIST.md).
2. Открыть [камеру на удалённом стенде](https://cyber102.94.41.87.102.sslip.io/index.html) на физическом iPhone в Safari и Android в WebView. С участником 3 проверить Basic Auth, системное разрешение `CAMERA` и выдачу `RESOURCE_VIDEO_CAPTURE` через `WebChromeClient.onPermissionRequest` для доверенного HTTPS-origin. Для показа подходит доступное подключение к интернету, локальная сеть на площадке — отдельный этап. [Проверка с телефонов](../docs/operations/deployment.md).
3. Проверить одиночный кадр и «Видеопроверку» с InternVL3. Выбрать интервалы 2, 5 и 10 секунд, проверить последовательную отправку кадров, рамку на последнем проверенном кадре, остановку и уход в фон. Записать устройства, версии ОС и WebView, сеть, задержку и результаты.
4. Проверить QR, повторную съёмку, отказ в доступе к камере и ответ на непригодный кадр. Подготовить встроенный пример для показа интерфейса. Автопроверка Chromium и мобильного WebKit с тестовым API уже прошла, физические устройства остаются в [чек-листе](CHECKLIST.md).

## День 2 — связать этапы осмотра

1. Сохранить выбранный по QR или вручную насос при переходе к камере. Дать оператору выбрать компонент, подтвердить или исправить наблюдение. Привязать рамку к идентификатору и размерам зафиксированного кадра.
2. Согласовать с участником по данным контракт признаков. Показать в карточке наблюдение камеры, данные датчиков и вывод правил отдельными полями. Отсутствующие и просроченные показания отображать как неизвестные. [Контракт интеграции](../docs/research/chapters/integration-contract.md).
3. Добавить путь сохранения реального осмотра с серийным номером, временем, подтверждёнными признаками и выводами. Повтор с тем же `requestId` должен возвращать одну запись. Исходный кадр по умолчанию остаётся в памяти. Текущий `POST /api/history` сохраняет демонстрационные сценарии. [Текущий контракт БД и API](../docs/architecture/database.md).
4. Проверить на двух устройствах связку «QR → насос → кадр → результат → запись». Если к показу готов только существующий журнал, показать сохранение на демонстрационном сценарии и указать это в протоколе. [Сценарий чекпоинта](../docs/checkpoints/checkpoint-1.md).
